# Pam 1,650 themed answers — reasoning and release plan

**Status: research-only, not live.** This is an experimental branch. Do not wire this roster into `scripts/build-pam-classic.mjs`, `src/client/mom-mode/engine.js`, the UI, or Vercel until the factual and gameplay gates below are satisfied.

## Objective

Increase possible answers from the validated 1,775 to a potential 3,425 **without turning Pam into a trivia lookup engine**. Keep the 20-turn budget, genuine uncertainty, an entertaining mix of general and discriminating questions, and the possibility of stumping her.

## Source inventory

`data/pam20q/expansion/roster-1650.br.b64` contains the **exact 1,650 rows** from the editorial workbook, including each displayed name, category, subcategory and source-supplied disambiguating context. The roster is Brotli-compressed JSON encoded as Base64 because the game repository does not need to carry a binary Excel dependency. Reproducibility is enforced by SHA-256 in `roster-manifest.json` and verified by `scripts/pam-thematic-lab.mjs`. It is not marked approved.

The roster has 150 cities, 100 countries, 300 monuments/paintings/sculptures, 200 landmarks, 200 bands, 200 people, 200 brands, 150 movies, 50 TV shows, 50 musicals and 50 car manufacturers.

## Why simply adding 1,650 names would damage the game

The spreadsheet is an **editorial name list**, not a verified yes/no knowledge graph. A category plus a subcategory does not distinguish the Beatles from the Rolling Stones, and the workbook provides no individual band traits. The same problem exists for TV shows, countries, people in the same occupation, etc. A 20 Questions engine cannot recover missing facts by adding more questions: each new question needs reliable known answers for each relevant target.

`node scripts/run-semantic-audit.mjs` builds a strictly conservative, **experimental** question set from workbook fields and measures how many subjects could possibly be distinguished. The candidate questions are not automatically editorially approved, and the exact/softened simulator is **not** a production game-win metric. The report records question text, per-category collisions, and an oracle sample. Unknown data stays unknown; no imaginary negatives are synthesized.

## Principles for making Pam fun

1. **20 turns, always.** A larger library is not a larger round. Guessing costs time. No list-selection or spelling-filter shortcuts.
2. **Broad to specific.** Establish whether the answer is a named person/place/media/brand before asking country, decade, material or creator. Never ask a category-specific question about an unrelated answer.
3. **Avoid the interrogation problem.** A run of six nearly synonymous regional or era questions feels like a search form. Use family cooldowns, semantic overlap checks, and a minimum expected information gain before choosing another one.
4. **Permit credible losses.** If evidence is missing or ambiguous, the model should be uncertain, not confident by default. Do not auto-exclude unknown targets on a No answer. Do not invent traits to chase benchmark numbers.
5. **Use human-interest questions.** Prefer `Was this person known for physics?` and `Was it created before 1980?` over database fields such as `Is the Wikidata country code CA?`. Every actual prompt ends in `?`.
6. **Use the game's voice.** Pam can sound confident, encouraging and a little cheeky in leads, hunches and reactions, but a character line must not change the underlying factual question.
7. **Keep obvious names approachable, obscure names challenging.** Do not target 100% model wins. Calibrate against a human-reviewed common/core tier and a genuinely hard tier.

## Factual enrichment contract

Every thematic target needs a human-readable `canonical_name`, aliases, primary category, **sources with URLs**, relevant positive facts, defensible negative facts or logically exclusive values, confidence, and review status. Facts are not generated by patterning from the answer's name. For artworks, sources should distinguish the exact work, medium and creator. For places, avoid conflating a city, its country and a monument located there. For people, avoid changing nationalities, professions and time periods by guesswork or string matching.

For a multi-value field such as a shared national border, not mentioning one country is **not** proof of a negative. Unknown assertions must be recorded as unknown. Verified oppositions between similar candidates matter more than the raw number of descriptive facts.

## Release gates

| Gate | Requirement |
| --- | --- |
| Source fidelity | Exactly 1,650 reviewed roster names and categories; stable identities; no duplicates against existing 1,775 without explicit editorial resolution |
| Question quality | Every prompt grammatical and punctuated, naturally answerable, meaningful, non-lexical, not a disguised guess |
| Factual quality | 100% of shipped yes/no/maybe claims grounded and reviewed, no unsupported negative inference |
| Pairwise separability | No unresolved same-signature targets among the candidates enabled for that release |
| Gameplay | Full new-target exact and two softened-answer test passes; pass target-specific 20-turn success thresholds calibrated by difficulty |
| Baseline | 0 wrong guesses introduced for the original 1,775 exact games and softened-answer benchmark; preserve question IDs/matrix semantics |
| UI | Original 20-turn structure remains, revised topical question text tested in UI and history, Pam voice reviewed |
| Device regression | Browser PWA offline/Chromium/WebKit checks remain green |
| Release approval | Explicit separate data-approval and deployment step; branch carries no production changes until gates pass |

## Phased implementation

**Phase A — completed:** exact spreadsheet roster, deterministic integrity hash, conservative semantic question generation, collision report, 20-turn oracle diagnostic, regression tests, deployment guard. **Not playable** yet.

**Phase B — next:** source-QID matching and explicit evidence collection for rows, category by category, beginning with places, films, science figures and stage works. Review contested entity matches, store URLs and exact claims, distinguish multi-valued attributes, add 3–6 meaningful independent traits per target where defensible and more where needed.

**Phase C:** assemble the 1,775 + approved subset with question-major 4-state weights and an explicit known mask, calculate information gain with coverage, use topical gates and family cooldown, then run full simulated games. Reject question rows whose only information is spelling, arbitrary name ordering or memorized ID.

**Phase D:** test with humans on desktop and phones (including uncertain and ambiguous answers). Calibrate the win-rate curve and reactions. Release only when pleasant to play and regression-safe. The expansion can ship in tested batches; the remaining candidates must not silently be labelled playable.

## Automated preflight findings — first workbook-only model

The GitHub CI preflight loaded **1,650/1,650** exact names and passed all original 1,775-answer integration tests. The first metadata-only semantic model has fewer than 10% individually distinguishable profiles. An early 293-filter run had 122 unique signatures; after adding explicit year filters and removing vague template questions, the local experimental model generated **345 candidate questions**, but only **147 uniquely distinguishable profiles**. An indicative, evenly spaced 104-name clean-answer simulation correctly isolated **1/104** targets. That is a meaningful failure: it shows how badly the list needs enriched, verified, distinguishing facts, not that the question-selection problem can be solved by changing constants.

The direct/near-label comparison identified **15** possible collisions with baseline names, mostly **homonyms** rather than repeat concepts. Examples include Apple the company versus an apple, Dove the brand versus a dove, The Kiss as several different artworks versus an ordinary kiss, and Alien the film versus an alien. Exact names and descriptions need review; those subjects must be separated through topic questions and never silently dropped.

## Source-backed enrichment research

`pam-wikidata-reconcile.mjs` uses the documented Wikimedia `wbsearchentities` interface to collect possible QIDs, contextual labels and public descriptions with provenance. Identical name strings can identify entirely different subjects, so proposed QIDs are **never automatically approved**. `pam-wikidata-facts.mjs` fetches explicit positive statements and preserves the property ID, claim ID, time precision and source. Missing statements and deprecated claims **do not become negative answers**.

The research pilot is `.github/workflows/pam-thematic-wikidata-pilot.yml`. It can query a balanced sample across all 11 categories and produces review-only artifact files. Wikimedia documentation: https://www.mediawiki.org/wiki/Wikibase/API and https://www.wikidata.org/wiki/Wikidata:Data_formats . These are sources for structured claims, not a blanket certification of entity matches or every real-world trait.

The goal of the next pass is to turn enough **reviewed** facts into discriminating profiles to pass category-level clean/softened 20-turn games. Question count is a consequence of separation and quality, not a quota that justifies making up questions.

## New technical building block: reviewed-evidence matrix

`scripts/pam-reviewed-fact-compiler.mjs` and `test/pam-reviewed-fact-compiler.test.mjs` define an isolated, review-gated compiler for future release. Once the human/source identity is verified, every yes/no cell must carry a review approval and a traceable evidence URL; imported research hints are never accepted as playable truth. **No change is made to the frozen 1,775-target runtime.**

Where a curator approves a *complete single-valued field*, such as a named city's verified present-day country, an opposite value is a defensible known **No**, not an invented negative. Multi-valued occupations, languages, creator lists, musical genres and other open taxonomies do not get negative assertions through absence or competing values. The compiler outputs a question-major matrix and explicit known mask, and rejects conflicting complete values, category-insensitive name hints, unknown candidate identifiers, unreviewed entity mappings and unapproved source claims. This gives the future game the kind of factual discrimination the workbook-only model lacks while safeguarding accuracy.

Related Wikidata QID values are decoded through source-linked English labels before editorial review. A claim can now carry both `value_id` and `value_label`; the label is a readable **unreviewed** suggestion, never proof. A failed label lookup remains a missing label, not a negative fact, and does not approve the parent entity.
## 2026-10-18: production evidence gate and question-quality work

The source roster remains **unreviewed**. The initial full Wikidata job exceeded the
one-hour GitHub Actions runtime after saving the first 550 responses (one-third of the 1,650 subjects). Of those responses, the initial matching heuristic
suggested 349 plausible single identities, 193 ambiguities and 8 missing
search results. A revised heuristic using descriptions, geographic context,
medium, artist/creator and film release year ranked **467** single plausible
identities, **75** ambiguities and **8** misses in the same saved 550 responses.
**This is NOT 467 factual approvals.** All matches remain suggestions pending
human or equivalent substantiated entity-level verification.

The remaining 1,100 subjects are researched in three bounded GitHub jobs
(`pam-wikidata-shards.yml`) with separate artifacts and explicit Wikimedia
request pacing. The initial 550 responses are retained as the original full-
lookup Actions artifact. Research results do not mutate the production model.

The earlier `collisionAudit` metric counted question fingerprints including a
question's *unknown* state, and reported 147 individually unique fingerprints.
This is a useful upper bound, not a valid proof of discriminability. The new
`knownOppositeAudit` requires a question with known yes for one candidate and
known no for the other; it finds only **136 individually separable** subjects,
**1,514** still ambiguous and **34,901 unresolved candidate pairs** under
spreadsheet metadata alone. Absence from Wikidata is **not** a reliable no.
This is a strict release blocker until source evidence fills in the matrix.

The `pam-thematic-reasoner.mjs` experimental chooser now maintains a posterior
probability distribution rather than treating `Probably` as an exact answer or
silently eliminating targets with missing data. It scores information-gaining
questions, tracks recently asked semantic families, honors the hard 20-turn
limit, never uses letters or spelling of the answer as a clue and withholds
confidence when facts are insufficient. Its synthetic fully-known 128-target
trials pass 128/128; it is **not** integrated into the existing Pam UI/runtime,
and the synthetic tests do not certify real 1,650-target success.

### Non-negotiable release gates

1. Verify identity QIDs and semantic reference (including common title/homonym
   collisions) and carry provenance and date precision in reviewed claims.
2. All shipped targets must have a known opposite to relevant confusable peers.
3. Original 1,775-target/156-question gameplay matrices remain unchanged;
   **zero** original-target correctness regressions are allowed.
4. Measure all new targets under exact yes/no and softened yes/no responses,
   with category-difficulty reporting and 20 turns at most, not only a sample.
5. Evaluate real question transcripts for repetitive country/decade questioning,
   inappropriate premature guesses, pacing, intelligible language, and Pam's
   character voice. Fewer questions should be required when the answer is easy;
   genuinely difficult answers must still be possible to use as stumps.
6. No production merge/deploy until full browser/mobile tests and the review
   gate are cleared. Passing lab unit tests alone is not production readiness.
